## המשימה (מקור: מסמך המטלה)

**The challenge:** Design and build an end-to-end flow that turns a recorded clinical encounter into a reviewable, signable note inside the provider's EMR.

**Background:** Sumit is a Hebrew speech AI company serving enterprise and public-sector customers, with deployments embedded in healthcare providers' clinical systems.

**Problem:** Oren Health (fictional) wants to eliminate manual documentation during patient visits. Physicians record the encounter from within Oren's EMR. Shortly after, a structured summary and clinical conclusions should be available in the physician's workspace for review and sign-off.

**Scope:**
1. **Design** – the end-to-end flow, from the encounter to a signed note.
2. **Build** – a working end-to-end product that runs on the provided encounters and writes into Oren's EMR.
3. **Validate** – how do you know it works?

**Deliverables:** live link · brief (flow + key product decisions) · build approach and tooling · optional walkthrough video.

**קבצי המשימה בתיקייה:**
- `transcripts.json` – 3 תמלולים גולמיים בעברית, כפי שחוזרים מ-`GET /jobs/{job_id}` של שירות התמלול. השדה `reference` הוא ה-`encounter_id`.
- `encounters.json` – תיק המטופל מה-EMR לכל ביקור (`GET /encounters/{id}`).
- `integration_spec.md` – ה-API של ה-EMR ושל שירות התמלול. **קרא אותו לפני שאתה מתחיל.**
- `design/` – העיצוב שלי (PDF). תיאור מילולי שלו למטה.

## Stack מומלץ

- **Next.js (App Router) + TypeScript + Tailwind.** ממשק בעברית, `dir="rtl"`.
- **ה-EMR המזויף ושירות התמלול המזויף:** API routes באותו פרויקט, שמממשים **בדיוק** את ה-endpoints, הפורמטים והשגיאות מה-spec.

- **העלאה לאוויר:** GitHub + Vercel. צריך כפתור/endpoint לאיפוס נתוני ההדגמה, כי הבוחן ירצה לנסות כמה פעמים.

## החלטות מוצר (כבר סוכמו – לממש כמו שהן)

### מה נכנס לסיכום
1. **שינוי דעה:** רק ההחלטה הסופית של הרופא נכנסת.
2. **נאמר מול נבדק:** מה שהמטופל סיפר → HISTORY. רק מה שהרופא בדק או מדד → EXAM. תלונה שלא נבדקה לא נכנסת ל-EXAM.
3. **שלילות** נשמרות כשלילות ("שולל כאבים בחזה").
4. **ייחוס:** מידע על אדם אחר (בן משפחה) לא נכתב כמידע על המטופל.
5. **מושמט:** מספרי זהות, שיחת חולין, מידע מזהה שלא נחוץ.
6. **תוכן רגיש** (מצב רוח, שינה) נכתב כפי שנאמר, בלי אבחנה שהמודל הסיק.
7. **תאריכים יחסיים** ("מאתמול", "3 ימים מהיום") מומרים לתאריכים מוחלטים לפי `started_at`.
8. **שמות תרופות** מנורמלים לשם הרשום באנגלית (התמלול משבש: "מט פור מין" = Metformin).
9. **זיהוי דוברים:** לא סומכים על `SPEAKER_00/01`. המודל מסיק תפקידים מהתוכן. ייתכנו יותר אנשים מתוויות, ותוויות שגויות.
10. **שפה:** עברית, שמות תרופות באנגלית.
- **אין אבחנות מומצאות:** ASSESSMENT מכיל רק את מה שהרופא אמר.

### נקודות לבדיקה ובטיחות
11. **מידע חסר:** אם פרט קריטי לא נקלט (למשל `[לא ברור]` במינון), נשאר שדה ריק מסומן, **והחתימה חסומה** עד שהרופא ממלא. **המודל אף פעם לא משלים או מחשב בעצמו.**
12. **"מסקנות קליניות" = נקודות לבדיקה, לצד הפתק ולא בתוכו.** הרופא מאשר או דוחה כל אחת. נקודה לא נכתבת לפתק אוטומטית.
13. **שלושה סוגי נקודות**, כל אחד בצבע אחר:
    - 🔴 **חוסם חתימה** – מידע חסר.
    - 🟠 **אזהרה** – פער מול התיק, בעיה קלינית שלא טופלה, תלונה שלא נבדקה.
    - 🔵 **עדכון תיק / לידיעה** – דברים שצריך לעדכן בתיק, או הבהרות.
14. **פער מול התיק:** כל מה שנאמר וסותר או לא מופיע בתיק (אלרגיה, משקל, תרופה) → אזהרה.
15. **בעיה קלינית שהרופא לא התייחס אליה** (למשל אינטראקציה בין תרופות) → אזהרה, בלי לשנות את מה שנאמר. לסמן אותה כ"הצעת AI, לא מערכת תומכת החלטה מאושרת".
16. **תלונה שעלתה ולא טופלה** → מתועדת כ"עלתה ולא נבדקה" + אזהרה.
17. **עדכון רשימת האלרגיות:** ה-API **לא מאפשר** לעדכן אלרגיות, רק לכתוב פתק. לכן הנקודה כוללת הנחיה "יש לעדכן ידנית את רשימת האלרגיות בתיק" ותיבת סימון לאישור הרופא (בעיצוב שלי: "אני מאשר שיש לבצע עדכון של התיק הרפואי"). אישור התיבה נדרש לפני חתימה. **לא לבנות עדכון אוטומטי של התיק.**
18. **עקיבות:** כל משפט בסיכום מקושר למזהי הקטעים בתמלול שעליהם הוא מבוסס.

### אינטגרציה עם ה-EMR
19. **מתי כותבים:** הטיוטה נשמרת אצלנו. ל-EMR נשלח `POST` אחד, בחתימה, עם `status: "signed"`. הסיבה: אין ב-API עדכון פתק, וטיוטות היו נכפלות.
20. **מי חותם:** `author_id` = `physician.id` של הביקור מה-EMR, לא מהתמלול. (בביקור 1 הרופאה בתיק היא ד"ר מיכל אביב, אבל הדובר מדבר בלשון זכר. זהות נלקחת רק מה-EMR.)
21. **שגיאות** (לפי ה-spec):
    - `401` token פג → הטיוטה נשמרת (localStorage), הודעה וכפתור "התחבר מחדש".
    - `503` EMR לא זמין → ניסיון חוזר אוטומטי, ואם נכשל, הודעה + הטיוטה נשמרת.
    - `409` הביקור נסגר → הודעה ברורה. (תיקון אחרי חתימה = addendum, לא לבנות היום.)
    - `422` → לא אמור לקרות, כי בודקים לפני שליחה (החלטה 22).
    - **פאנל מפתחים מוסתר** שמאפשר לדמות כל שגיאה בשליחה הבאה, כדי להדגים בסרטון.
22. **מגבלות פורמט:** טקסט נקי בלבד, עד 2,000 תווים לסקשן, רק 7 הקודים מה-spec. סקשן ריק לא נשלח. בדיקה בצד שלנו לפני שליחה.
23. **פרטיות ופריסה:** ה-EMR יוצא רק לדומיינים מאושרים. בפרוטוטייפ משתמשים ב-API חיצוני, ונציין ב-brief מה היה נדרש בייצור. לא לבנות.

### חוויית הרופא
24. **אין תמלול בזמן אמת.** ה-API עובד על קובץ שלם, והמטרה היא שהרופא יסתכל על המטופל.
25. **כתיבה ידנית:** אפשרות משנית לפני הקלטה, נעלמת בזמן הקלטה.
26. **אחרי עצירה:** הסיכום נוצר. במסך הסקירה אפשר "מחיקה וכתיבה ידנית".
27. **אחרי חתימה:** הפתק נעול ומופיע ב"סיכומי ביקורים".

## פלט המודל (הצעה ל-schema)

```
speaker_roles: { "SPEAKER_00": "physician", ... }   // + הערות אם התוויות שגויות
sections: [
  { code: "REASON" | "HISTORY" | "EXAM" | "ASSESSMENT" | "PLAN" | "MEDICATIONS" | "FOLLOW_UP",
    sentences: [ { text, source_segments: [מספרי קטעים], missing?: { field, reason } } ] }
]
review_points: [
  { type: "blocking" | "warning" | "chart_update" | "info",
    title, detail, source_segments, related_section, requires_ack: boolean }
]
```

מזהה קטע = האינדקס שלו במערך `segments`. מעביר למודל את התמלול עם מספרי הקטעים, את תיק המטופל ואת `started_at`.

## שלבי הבנייה (שלב אחד בכל פעם, לחכות לאישור שלי)

1. **שלד + EMR מזויף:** פרויקט, מסך בית, מסך מטופל עם נתונים אמיתיים, API routes של ה-EMR לפי ה-spec (כולל ולידציה ושגיאות).
   ✔ אני יכולה לעבור בין 3 המטופלים ולראות את התיקים.
2. **הקלטה + תמלול מזויף:** פס הקלטה, השהיה, סיום, מסך עיבוד, ו-API של שירות התמלול עם סטטוסים.
